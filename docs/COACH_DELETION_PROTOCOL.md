# Coach Push 删除一致性，协议 1

## 范围

仅补现有云端提醒删除在另一客户端缓存中的一致性，不新增UI、完整收件箱或通用同步实体。Insight反馈与本机生成提醒保持原行为。当前云端列表仍只返回最新50条，列表缺席从来不表示删除。

新迁移 `20261012170000_coach_push_tombstones` 只创建3个触发器：Push删除在同一SQLite事务写入现有SyncTombstone（entity=coachPushes），禁止同所有者复用删除ID，禁止现有Push改变ID/所有者。没有回填、删旧数据或重写已发布迁移，不往SyncChange发出旧v2客户端不认识的实体。

DELETE /api/coach/pushes/:id 在触发器未就绪时503并保留数据；已删且同所有者墓碑存在的重复请求返回200。其他账号/从未有删除事实的ID仍404，不能凭未知ID制造墓碑。写墓碑失败会回滚原Push删除。删除整个账号时既有FK级联会移除该账号全部墓碑，不保留私人残留。

## 有界核对

POST /api/coach/pushes/deletion-status，JSON为 protocol=1、ids=1至100个互不重复的原始ID，单ID最多256个UTF-16代码单元，不trim或转换。认证/期待账号校验仍走统一中间件。返回 protocol=1 与 deletedIds，只含当前用户、请求集合中的确切墓碑；未知、其他用户、仍活记录都不返回，不能用它判断其他账号ID存在性。响应no-store；账号每分钟120批上限。

前端对当前账号缓存 origin=cloud 的合规ID串行分批核对，不是只核前100。每批JSON UTF-8体积最多12KiB（低于服务端最低可配16KiB），每次最多100批，并将环形 afterId 进度与已确认删除一并写入当前账号 settings；进度绑定owner与dataEpoch，可跨重载继续。列表新增、旧cursor记录消失时仍按排序环绕覆盖，遇限额不反复从前缀开始。超过256代码单元、空或非字符串历史ID原样保留、不查询、不截断，并记录不含ID/正文的coach运行诊断；这些记录的云删除尚未核验，不让异常ID卡住其他批次。每批严格核响应协议、ID类型/重复/请求集合；成功批次可应用，失败或畸形批次及后续未查项保留。重试自然只核剩余缓存项，避免永久卡在前100。暂停/旧加载/账号代次改变后停止后续批次，迟到旧结果不应用。

删除与当前账号本地 coachPushDismissed 墓碑在同一IndexedDB事务提交，迟到旧列表不会复活；仅明确标记cloud且仍是当前记录的ID才删。origin=local、无origin旧记录、分页外活记录均保留。删除查询失败不丢已缓存证据，也不把可达服务器本身当删除证明。

## 升级、备份、回退

旧安装走原启动器：先验证prestart备份，再Prisma migrate deploy。新迁移对现存Push无数据变换。离线旧库导入器固定目标迁移SHA更新为11条，并继续原支持边界、原ID/所有者/原文字节规则；不自动激活候选。

SQLite备份天然包含SyncTombstone和新触发器；浏览器墓碑随账号settings导出。协议启用之前已经硬删的提醒没有可追溯事实，不能补假墓碑或自动清旧缓存。旧应用版本不懂新核对端点，仍可能显示自己旧缓存，需更新客户端后验证。回退旧代码时保留新数据库schema，不删除墓碑/触发器；若需要真正回退数据库必须封存两端并保护回退点之后新写入，不直接覆盖。
